# F23 development cycles — v1 interface

The feature is an opt-in coding controller with settings at global/per-plan scope. It is separate from SuperAgent message delivery. `harness/bin/development-cycle.mjs` is the selected SuperAgent entry; it wraps the existing tracked worker-launch path through trusted host ports. The app at `/development-cycles` exposes pending/applied/refused settings, policy preview, run findings, evidence, budget and coverage. It installs no production runner.

## Contracts and trust

`contracts.mjs` supplies equivalent runtime validation for versioned settings, contracts, budgets and approvals. Canonical JSON hashes pin semantic content. `policy.mjs` unions named requested/mandatory requirements; `POLICY.md` publishes the exact risk and severity rules for owner review. T2 is the default. Unsupported schema/adapter versions fail closed. Active runs never reread settings to weaken their contract.

`store.mjs` owns one private namespace at `<data>/development-cycle/state.json`. This is the sole canonical settings/request/run store; no duplicate modes key or browser storage. Atomic checksummed snapshots contain the ordered event history and evidence manifest. A synchronous exclusive transaction lock and optimistic run/settings revisions reject competing writers. Completed lock directories and test roots are archived. A stale lock requires explicit dead-owner recovery; malformed/unknown ownership stays held. Pending partial files are never admitted.

The builder cannot issue an evidence seal or approval. The trusted host captures commands, results, source/test identities and artifacts. `SuperAgentWorkerAdapter` uses separate roots and independent role copies, rejects symlinks/special files, protects the accepted test manifest, checks the complete imported diff against write scope, and requires real confinement and admission ports before invoking the shipped worker launcher. Hash/diff checks supplement OS confinement; they do not replace it. Host-run test commands also require confinement, since tests execute code.

Independent core tests must be supplied as a host-verified bundle: `{testsHash, requirementsHash, authorContext, derivation:'contract-only', protected:true}`. The `requirementsHash` is the hash of the normalized contract checks. The `verifyTestBundle` port must verify actual protected provenance. A different model/session label cannot supply that proof. The fresh validator must add new `validator-tests/*.test.mjs` files; existing candidate/core tests cannot change. Each added file declares its required case names in a single `// cycle-required-tests: ["case name"]` JSON header. The host captures that declaration from the immutable validator artifact before running it; absent, empty, duplicate or malformed declarations hold validation. Added tests run as extra host-configured Node checks and appear in the sealed evidence manifest. A failing probe returns to repair. Every added test is captured under the host's private evidence root with its immutable bytes, content hash and required-case inventory. The append-only receipt history retains these obligations even when results fail or become stale. Every later role reinstalls and runs retained tests; builders receive bounded assertion details (case, location, expected/actual, command and execution gaps) and get the protected files only after they exit. New validators must use new filenames and cannot replace earlier tests. Admission checks the complete historical inventory against current-candidate results, so adding passing B never retires failing A. Restart verifies both code snapshots and retained artifact hashes. Use a stable host sealer key across reconstruction.

Retiring a mistaken validator requires `correctTests` with `validatorRemovals:[{name,hash}]` in the fully hashed independent-reviewer correction. Old/new core-test identities (which may remain equal for an explicit validator-only retirement), exact removed artifact identities and the existing approval requirements remain binding; the receipt history is retained, prior evidence invalidated, and review/baseline rerun. Ordinary repair, resume and budget approvals cannot retire validator obligations. Use a new filename for replacement coverage.

## Host ports

A private ports module exports `schemaVersion = 1` and async `createCyclePorts({dataRoot})`:

| Port | Contract |
|---|---|
| `clock()` | Milliseconds, wall clock; injected for tests. |
| `guards(contract)` | Fresh existing restrictions; `{allowed:true}` only after owner/provider/resource/role checks. |
| `telemetry(contract,{operation})` | Fresh `usage:{runId,at,complete:true,liveAccounting:true}`, plus `activeUsage` for the pending operation; separate real provider meters and calibrated estimated window rates. |
| `runner({operation,run,signal,graceMs})` | Execute exactly one admitted stage; return a host-sealed evidence record plus findings/usage whose hashes are included in it. |
| `terminate({operation,runId,reason})` | Existing supported process-tree stop/checkpoint action; never a new unrelated job or global STOP. |
| `verifyUsage(snapshot)` | Authenticate host cumulative snapshots; mandatory for selected cost/window metrics, key inaccessible to workers. |
| `verifyEvidence(evidence)` | Verify trusted provenance/seal; key inaccessible to workers and stable across restarts. |
| `eligible(run)` | Existing Jev/provider/role/hold admission for the fixed same-tier alternate map. |
| `notify(event)` | Existing SuperAgent infrastructure; deduplicate by stable event ID. Delivery failure retains the outbox item. |
| `verifyApproval(approval)` | Authenticate issuer and event integrity; controller additionally checks exact run, candidate, contract, type, scope, authority and expiry. |

Adapter-specific `admitLaunch` must return the admitted harness/model/tier, tracked/gated status, timeout and isolated launch environment. `isolate` must establish inaccessible evidence/test authority and return execution controls plus an abort-aware supported `launch` function. These are trusted deployment interfaces, not user-settable booleans. Default app behavior has no such ports and cannot dispatch.

`executeCommandChecks` is a Node fixture/reference check executor, using argv arrays without a shell. A production isolation port must wrap check execution with the same confined environment. Configure stage-specific checks for failure analysis, independent author/reviewer verification, and boundary/adversarial checks. Ordinary check definitions apply after baseline and to coding/validation stages. Meaningful red requires completed `process.execPath --test` execution with structured Node runner assertion events from explicit `node:test` cases. Each Node test check must supply a trusted `requiredTests: [{file:"check.mjs", name:"required case"}]` inventory from the reviewed test bundle. Case names must be unique within their file. Every listed case must have exactly one concrete completed pass/fail event from that file, and the file must emit its own normal runner summary. The inventory is never learned from candidate execution. Missing manifests, filtered/conditional omissions, skipped/todo cases, synthetic file wrappers and suite containers cannot satisfy it; non-required optional skips remain allowed. Fresh validator checks use the same rule. This reference reporter distinguishes isolated-child events (ordinary decoded objects) from host file wrappers (null-prototype records), including on Node 22 before `entryFile` was available. Concrete test types are required except on Node 22.13/22.14, where ordinary cases omit the type and suites still carry `suite`. Per-file and overall runner summaries remain mandatory. The compatibility checks are verified on Node 22.13.0, 22.23.5 and 24.22.3; unsupported event shapes fail closed. The host replaces display reporters with its own protected reporter; test stdout/stderr is captured as data and cannot issue verdicts. A generic failed TAP entry, a top-level uncaught assertion or assertion-looking text is insufficient. Any startup, collection, hook, cancellation or infrastructure failure holds the entire check, including when another test asserts. Non-test commands may pass with exit zero, but their nonzero exits remain unclassified; other tools need a trusted structured executor. An explicit expected nonzero exit can prove incident reproduction only with that evidence. Timeout, abort, signal termination, spawn errors, output-buffer exhaustion and syntax/dependency/collection failures never count as red or expected-exit success. Each check records process completion, termination, signal and the original error code; a process without a numeric exit retains `exitCode: null`. A runtime with different test tools supplies its own trusted check executor.

The reference executor also protects assertion semantics before candidate imports. It installs host-owned bootstrap/runtime preloads, freezes intrinsics and both assertion entry points (including `Assert` prototypes), locks Node test exports and each context assertion table before user hooks, and disables assertion registration, mocking and snapshots. Native addons, module-loader changes, private bindings, debuggers and other instrumentation entry points are refused. The bootstrap preserves error-constructor data descriptors so genuine assertion failures retain their structured metadata across the runner boundary. Completed green checks require no positive assertion-failure count.

This protected runtime is intentionally restricted to **Node 22.13+ (22.x), Node 24.x and ESM modules**. It refuses other test executables, CommonJS candidate modules, custom preloads/loaders, unrecognized CLI flags, Node runtime environment overrides, and imports of `module`, `vm`, `v8`, `inspector`, `async_hooks`, `diagnostics_channel`, `child_process`, `worker_threads` and `cluster`. It accepts test file arguments, name/skip patterns, timeout/concurrency controls and presentation-reporter choices (replaced by the host reporter). Ordinary ESM tests, hooks, nested cases and `node:assert`/`t.assert` checks work; explicit non-test commands retain their earlier behavior. Projects needing unsupported APIs must supply a separately trusted executor with a protected check runtime. The async loader hooks support the minimum Node version and enforce the same denied builtins and ESM-only rule. Both named and default assertion registries are protected (they can be separate objects on Node 22). The preloads, loader hooks and reporter are host authority and must be inaccessible to candidate writes; OS confinement is still required. This restriction is not a general Node sandbox or production-runner installation.

## Budgets and repair

Targets are hours of wall time, versioned API-equivalent dollars and estimated `window:provider:5h|7d|1mo` percentage points. No spending target is implied. The CLI requires explicit targets. Every child/role contributes leaf usage once under the same run. Cache reads/writes are separately priced. Cost is an estimate, not a subscription invoice or billing permission.

Cost/window targets require a host-authenticated cumulative accounting source before dispatch. Each signed `activeUsage` snapshot contains `{schemaVersion:1,runId,operationId,provider,epoch,sequence,at,cumulative:true,tokens,price,source,sourceHash}`. Tokens have separate input/output/cacheRead/cacheWrite counters and a pinned versioned price. The operation's provider, meter epoch and price cannot change; sequence/timestamp and every counter must be monotonic. Exact repeats are idempotent. Foreign run/operation snapshots, resets, conflicts, missing verifiers, unavailable sources and snapshots older than the pinned freshness limit hold the run. Accounting source requests time out within the lesser of one second and checkpoint grace. The controller polls at that same interval and then requests bounded cancellation within checkpoint grace; this is a checkpoint barrier, not a provider billing cap.

`SuperAgentWorkerAdapter.snapshotUsage({runId,operationId})` wraps a separately trusted `observeUsage` host port and seals its normalized observation. It never treats worker prose or unscoped provider-account deltas as live consumption. The built-in completed Codex JSON parser supplies final usage only; it does not supply an in-flight meter. Without an independently installed host meter, cost/window runs remain held. Hours-only runs need no live-usage capability.

Persisted operation snapshots contribute alongside completed ledger entries, with one contribution per operation. Authenticated final receipts (including explicit zero-cost receipts for local-only stages) settle the same operation, must cover its last observed counters, and replace its provisional contribution without double-counting. Usage is retained even if workflow evidence is rejected. Snapshot state survives pause, cancellation, restart and harness handoff. Accrual stores both percentage points and the dollar basis from the same observation, so a later final receipt or provider-window reset cannot erase or reprice earlier consumption.

A learned window rate requires fresh account-exclusive, nonoverlapping meter intervals with the same reset identity and known token-priced work. Shared account deltas are rejected for calibration. Missing/stale/reset telemetry pauses selected metrics. Accrued points and dollars survive window changes, role switches and resume. The real provider meter remains a separate guard.

The first reached target/hard ceiling records a dispatch barrier, preserves checkpoint identity and notifies the SuperAgent. The controller requests bounded termination after pinned checkpoint grace and retains unknown results for reconciliation; it never replays an uncertain call. Ordinary extensions need a scoped SuperAgent/owner decision. Owner hard ceilings require owner authority. No approval clears unrelated hard restrictions.

Resume and budget-extension approvals cannot replace accepted tests. The trusted caller must first use `controller.correctTests(runId, correction, approval)` with an authenticated independent-reviewer approval scoped to the hash of the full correction (old/new hashes and change scope). The correction records that approval and invalidates prior evidence; a paused run stays paused until separately resumed, then reruns test review/baseline even when the candidate also changed. Contract-changing corrections need owner authority and hold for a new contract; resume cannot clear that hold. In-flight operations require reconciliation before any correction. Reconciliation while paused updates only the saved continuation to the result's next stage and retains the pause, live hold and approval requirements. Restart and approved resume use that reconciled continuation; duplicate receipts cannot append evidence or usage twice.

An episode is anchored to the contract repair goal and stable invariant fingerprint. One effort bump (never Max), then one eligible alternate, then scoped SuperAgent review permission. Discovery is diagnostic progress and does not satisfy admission. There is no fixed repair-count cutoff. Resolved findings require confirmation; MED/LOW deferrals require reason, accountable owner, evidence, backlog and trigger. Mandatory failures always block.

## Verification and integration

Run `node --test app/tests/development-cycle-*.test.mjs`, `npm run test:development-cycle:browser`, and `cd app && npm test`. The browser check requires an installed Playwright module/browser: set `PLAYWRIGHT_MODULE` to the module directory and `PLAYWRIGHT_CHROME` to the Chromium executable when they are outside normal resolution. Its source is `app/tests/development-cycle.spec.mjs`; include it in every review/export candidate along with the unit tests. It binds only to localhost ports 19360–19379 and verifies T3 ordinary fresh-validation preview as well as the UI failure/interaction cases. The test launcher, HOME, data, provider callbacks and tracking are isolated; no actual model is launched. The adapter fixture exercises the actual worker-launch process with fake CLI/tracker executables, including T3 ordinary and the complete critical-risk path. This is fixture coverage, not an observed live coding delivery or independent final audit of F23 itself.

The merge surface is `app/server.mjs` (one mounted route) and `app/index.html` (one navigation link). All feature logic stays in this directory and the CLI. Reconcile against the actual future app, reject incompatible schemas, and rerun final verification there. The staged external shim and installation/rollback instructions live under `_staged-harness/`; nothing installs automatically. No feature version/tag/release is published here.
